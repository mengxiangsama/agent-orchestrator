# 优惠券订单支付模块：从设计验收到实现交接

> 本文是完整的教学示例，不是已运行的项目、工具记录、支付结果或验收证据。所有用户、订单、商品和金额都是合成样本。任务编号是逻辑编号，不是真实 agent ID。文中的 `accepted` 节点用于说明何时允许推进；真实使用时必须由主智能体检查实际交付物后记录。

编排依据见 [Skill](../SKILL.md)、[分发规范](../references/dispatch.md)、[任务与版本记录](../references/ledger.md)、[验收规范](../references/acceptance.md)和[运行能力与降级](../references/runtime.md)。下文的业务文件路径属于合成项目，均为相对路径；本 Skill 仓库不承诺存在这些实现文件。

## 1. 完整的合成用户请求

下面整段是本例假设用户明确给出的请求。业务规则的来源是这段请求，不能将它们当作 Skill 的通用默认值，也不能用于补全真实用户没有说明的支付规则。

> 请在一个用于教学的本地项目里设计并实现“优惠券订单支付模块”。先提交设计，由主智能体验收设计后再安排实现，最后由主智能体整合检查。无需每一步都向我请求批准；如果关键规则发生变化，要暂停受影响的工作并说明影响。
>
> 每次只处理一个订单、只支持一种币种 CNY、每单最多一张固定金额优惠券。不做库存、积分、税费、多商家拆单、退款、部分支付、订单取消、超时关单或多次支付尝试。语言不限；为让本例命令可复现，可以选择 Python 3.11 及标准库，以 SQLite 保存本地状态，用内存中的模拟支付适配器做测试。不要接真实支付服务，不安装第三方依赖，不联网、提交 Git、发布或部署。
>
> **R1 金额和输入。** 所有金额单位都是分，使用整数，拒绝小数、数字字符串和布尔值。每个商品单价、运费、券门槛与券面额均在 0 到 1,000,000,000 分之间，其中券面额必须大于 0；数量是 1 到 100 的整数，至少有一行商品。商品金额之和及最终应付金额都不得超过 1,000,000,000 分。只接受 CNY。示例时间统一由可注入时钟提供，采用 UTC；不要依赖真实当前时间。
>
> **R2 优惠顺序。** 商品金额 `goods = Σ(unit_price × quantity)`。先用优惠前的 goods 判断券门槛；满足条件时 `discount = min(coupon_value, goods)`，没有使用券时 discount 为 0。运费不参加门槛判断，也不被优惠券抵扣。应付金额 `payable = goods - discount + shipping`。不四舍五入，不出现负应付金额。
>
> **R3 有效券。** 券必须属于当前下单用户，状态为 AVAILABLE，且创建订单时满足 `valid_from <= now < valid_until`、`goods >= threshold`。明确提交了无效券就拒绝下单，不静默改成无券下单；未提交 coupon_id 才按无券计算。用户、商品价格和券数据来自本地合成夹具，不接外部会员或商品服务。
>
> **R4 占用和落单。** 同一张券最多被一个订单持有。创建订单和将券由 AVAILABLE 改为 RESERVED 必须在同一个本地事务中提交；失败则一起回滚。订单保存商品金额、优惠、运费、应付金额、券 ID 和规则版本的不可变快照。券的有效期只在创建时校验；合法占用后不会因等待期间到期而自动释放。支付失败释放后，再次使用必须重新校验有效期。
>
> **R5 创建幂等。** 调用方提供非空 request_id，按 user_id 与 request_id 组合去重。重复提交相同订单内容，返回原订单，不重新占券或创建支付；内容不同则返回 IDEMPOTENCY_CONFLICT。内容相等指有序商品行中的商品 ID、单价、数量，以及运费、币种和 coupon_id 全部一致。订单即使已关闭，使用原键重试也只返回原订单；新订单必须换键。
>
> **R6 零金额。** payable 为 0 时，在创建事务内直接将订单记为 PAID、使用的券记为 USED，不创建支付记录、不调用模拟支付。该场景响应中的 payment_id 为 null。订单已支付是后续模块可以读取的结果；本例不实际发货或发送消息。
>
> **R7 正金额支付。** payable 大于 0 时先创建 WAIT_PAY 订单；显式调用 start_payment 才创建唯一 payment_id 并请求一次本地模拟支付。每个订单只有一次支付尝试，重复 start_payment 返回现有支付状态，不再次请求适配器。模拟适配器只返回 PENDING、SUCCEEDED、FAILED 或 UNKNOWN；调用异常或超时记 UNKNOWN。创建支付记录应先持久化；如果进程在调用附近中断，重试也不再次请求，保持 UNKNOWN 等待人工提供模拟结果。本例只保证本地记录幂等，不声称外部支付恰好执行一次。
>
> **R8 成功、失败和未知。** 支付 SUCCEEDED 时，在同一事务中更新支付为 SUCCEEDED、订单为 PAID、所用券为 USED。支付 FAILED 是明确的最终失败，在同一事务中更新支付为 FAILED、订单为 CLOSED、券恢复 AVAILABLE。PENDING 或 UNKNOWN 时订单仍为 WAIT_PAY、券仍为 RESERVED。不能把异常、无回调或等待超时当成失败、释放券、重复扣款或自动关单。不做自动重试、后台查询或定时任务。
>
> **R9 回调幂等和验证。** 回调仅是单元测试调用的本地函数，不暴露公网端点，不处理真实签名或凭证。参数必须含 event_id、order_id、payment_id、currency、amount 和 result。result 只接受 SUCCEEDED、FAILED；amount 必须等于该订单快照的 payable，currency 必须是 CNY，订单和支付 ID 必须匹配。缺失、类型错误、未知 ID、金额/币种错误均返回明确错误且不改任何状态。先完成上述校验，再检查事件幂等。event_id 全局唯一：同一个事件及相同内容重复返回原结果；通过基础校验但相同事件 ID 的内容不同，返回 CALLBACK_CONFLICT。不同事件重复报告同一个最终结果也不得再次改变订单或券。已经有最终结果后收到相反结果，返回 FINAL_STATE_CONFLICT，保留原结果并记录冲突供人工查看，不自动退款或改判。
>
> **R10 观察未知态。** 只允许测试或教学操作者显式调用本地回调函数，给出模拟适配器的最终结果，推进 PENDING/UNKNOWN；没有新结果就保留原状态。对已最终失败的旧订单收到迟到成功，同样按最终态冲突处理；不能占用已经释放给其他订单的券。没有支付记录的零金额订单收到支付回调应拒绝。
>
> **R11 交付和验证。** 设计写入 `docs/coupon-payment-design.md`；实现只写 `src/coupon_payment/` 和 `tests/coupon_payment/`。主智能体的整合说明只写 `docs/coupon-payment-integration.md`。请覆盖整数校验、门槛和有效期边界、券竞争、创建幂等、零金额、支付请求幂等、重复与冲突回调、明确失败、未知态和事务回滚。运行实际能够运行的本地测试；不能运行时列明原因，不宣称运行通过。设计请求如果改成“仅设计”，只交付设计文档，不写业务代码、测试或整合文档。

这些规则刻意限制了范围。例如，真实支付的签名、对账和退款均不在本例内；不能把这个教学模块宣称为可直接接入真实资金的方案。

“设计执行者”和“实现执行者”不是 agent ID。实际派发前按运行规范确认工具能力并记录工具真实返回值；本例不提供杜撰的工具名称。若不能委派，由主智能体依次执行 D、I、M，仍保留同样的验收门槛。不得用新聊天替代子智能体。

## 3. D 的设计交付应包含什么

以下是设计 v1 应明确的约定，均来自 R1–R11 或本节公开的实现选择；不是另加业务规则。选择 Python 仅用于展示可核验的本地命令，Skill 同样适用于其他语言。

### 接口和数据

本例不依赖 Web 框架，使用进程内服务方法。模块采用 `src/coupon_payment/` 布局，测试从项目根目录通过 `PYTHONPATH=src` 发现模块。

| 接口 | 输入 | 返回和约束 |
| --- | --- | --- |
| `create_order` | user_id、request_id、currency、非空 items、shipping、可选 coupon_id；items 每行含 product_id、unit_price、quantity | order_id、order_status、goods、discount、shipping、payable、rule_version、可空 payment_id；按 R5 返回原快照或幂等冲突 |
| `start_payment` | order_id | payment_id、payment_status、order_status；零金额返回 PAID，两个 payment 字段均为空；已关闭订单不创建新支付 |
| `apply_callback` | R9 的六个必填字段 | 应用结果、order_id、payment_id、最终状态；验证失败时返回设计错误码 |
| `get_order` | order_id | 已保存的订单快照及当前状态；未知订单报错 |

标识符均为非空字符串；金额/数量使用 R1 的严格整数约束。金额越界、参数类型错误使用 `INVALID_ARGUMENT`；无效券使用 `COUPON_NOT_USABLE`；不存在的订单/支付使用 `ORDER_NOT_FOUND`/`PAYMENT_NOT_FOUND`；回调关联、金额或币种不一致使用 `CALLBACK_MISMATCH`。R5、R9 中明确指定的三个冲突错误码保持原名。错误码选择属于接口约定，由 D 验收后固定，不能在 I 中私自改名。

订单表保存用户、创建幂等键、规范化请求内容、金额快照、可空券 ID、可空支付 ID、状态及 `rule_version=1`。设置 `(user_id, request_id)` 唯一约束；请求内容比较保留商品行顺序。基础参数校验后先查创建幂等记录；命中同内容时返回原快照，不因券已经被本单占用、使用或到期而再次拒绝。只有新订单才执行券资格校验与占用。

券表保存所属用户、门槛、面额、有效区间、状态和可空 reserved_order_id。支付表对 order_id 设置唯一约束，存储 payment_id、amount、currency、状态。回调事件记录以 event_id 唯一，保存规范化内容及处理结果；冲突记录保存冲突种类和关联 ID，不包含凭证或真实个人信息。

### 状态和事务边界

| 触发 | 订单状态 | 券状态（使用券时） | 支付状态 | 事务约束 |
| --- | --- | --- | --- | --- |
| 创建正金额订单 | WAIT_PAY | RESERVED | 无支付记录 | 落单和占券一起提交 |
| 创建零金额订单 | PAID | USED | 无支付记录 | 落单和用券一起提交，不调用适配器 |
| 首次开始支付 | WAIT_PAY | RESERVED | 先持久化 UNKNOWN | 每单唯一支付，先提交记录再调用本地适配器 |
| 模拟结果 PENDING | WAIT_PAY | RESERVED | PENDING | 只更新匹配的非最终支付 |
| 调用异常或结果 UNKNOWN | WAIT_PAY | RESERVED | UNKNOWN | 保留占用，不补发请求 |
| 成功结果或合法成功回调 | PAID | USED | SUCCEEDED | 支付、订单、券的最终变化在同一事务 |
| 明确失败结果或合法失败回调 | CLOSED | AVAILABLE | FAILED | 支付、订单、券的最终变化在同一事务 |
| 同结果重复回调 | 保持 | 保持 | 保持 | 记录幂等响应，不重复执行最终变化 |
| 相反最终结果 | 保持 | 保持 | 保持 | 记录冲突，返回 FINAL_STATE_CONFLICT |

无券订单的券操作为空操作。只有 reserved_order_id 匹配当前订单时才能消耗或释放券；迟到回调不得影响别的订单占用。最终态不可逆。零金额订单没有支付记录，所以不能通过支付回调再次更改状态。

设计选择使用 SQLite 事务和带状态条件的更新保证本地一致性。券竞争必须在同一数据库上的独立连接间验证，不能只测单个内存对象。业务验证失败或注入的本地数据库故障应回滚该事务；不得留下“有订单但没占券”或“订单已支付但券仍占用”的半成品。

适配器调用放在创建支付记录的事务之外。调用抛错只影响观察状态，不触发失败释放。适配器返回与回调共用最终态迁移约束；若最终回调已经先到，较晚的 PENDING/UNKNOWN 不能覆盖它，矛盾的最终结果只能记冲突。该约定避免两条结果入口产生不同状态规则。

回调先完成字段、关联及金额校验，再检查事件幂等。结构无效或关联不匹配不写任何记录；有效的新最终事件与状态更新原子提交。相同 event_id、相同内容返回已存处理结果；相同 event_id、不同内容返回 CALLBACK_CONFLICT。不同事件携带相反最终结果时，可保存冲突处理结果与冲突记录，但不得修改订单、支付或券的业务状态。

### 可观察的验收用例

下面均为**预期行为**，不是测试输出。固定教学时钟为 `2030-01-01T12:00:00Z`；有效券的示例区间为 `2030-01-01T00:00:00Z` 到 `2030-01-02T00:00:00Z`。样本用户使用 `user-demo`，商品使用 `product-demo`。

| 编号 | 合成输入或事件 | 预期 |
| --- | --- | --- |
| T01 | 商品 5000 × 2，运费 500，券门槛 10000、面额 3000 | goods=10000，discount=3000，payable=7500 |
| T02 | goods=9999，运费=500，券门槛=10000 | 拒绝该券，不因含运费总额超过门槛而放行 |
| T03 | goods=2000，运费=500，券门槛=0、面额=3000 | discount=2000，payable=500，运费保留 |
| T04 | 同 T03，但运费=0 | 订单 PAID、券 USED、payment_id=null，适配器调用次数 0 |
| T05 | 不传券，goods=0、运费=0 | 零金额订单 PAID，无券变化、无支付记录 |
| T06 | amount 或 unit_price 为小数、字符串、布尔值，数量为 0；goods 或 payable 越上限 | INVALID_ARGUMENT，无订单或券副作用 |
| T07 | now 等于 valid_from；now 等于 valid_until | 前者可用，后者不可用；另检查非所属用户、RESERVED、USED 券均拒绝 |
| T08 | 相同用户和 request_id，内容相同；随后改变数量再提交 | 首次重试返回同一订单；内容变化返回 IDEMPOTENCY_CONFLICT |
| T09 | 两个独立数据库连接为不同订单争用一张可用券 | 只有一个订单占券成功，另一个不落单、不占券 |
| T10 | 同一正金额订单连续或并发调用 start_payment | 支付记录至多一条，适配器至多调用一次；返回同一 payment_id |
| T11 | 成功回调重复同事件，再以另一事件重复成功 | PAID/USED/SUCCEEDED 保持不变，无重复业务变化 |
| T12 | 回调 event_id 重用但内容不同；或金额、币种、关联错误 | 对应冲突或不匹配错误，不更改业务状态；字段缺失/类型错误也拒绝 |
| T13 | PENDING 后收到明确 FAILED | CLOSED/AVAILABLE/FAILED 同步提交；原创建键重试仍返回关闭订单 |
| T14 | 调用异常、超时或模拟 UNKNOWN；重复 start_payment | WAIT_PAY/RESERVED/UNKNOWN 保持，支付请求不重发 |
| T15 | UNKNOWN 后合法成功；PAID 后再收到失败 | 先原子到 PAID/USED/SUCCEEDED；再报最终态冲突并保留成功 |
| T16 | 失败释放券，另一订单合法占用，旧订单迟到成功 | 旧订单报最终态冲突，不改变新订单的券占用 |
| T17 | 已占券在等待时过期后支付成功；失败释放后尝试新订单 | 前者仍可成功使用；后者因券已过期拒绝 |
| T18 | 创建事务或最终状态事务中注入数据库错误 | 所属事务完整回滚；不把数据库异常当作支付最终失败 |
| T19 | 零金额订单收到回调；未知 order_id/payment_id | 拒绝，不创建支付或改变已有状态 |
| T20 | 最终回调先完成，适配器较晚返回 PENDING/UNKNOWN 或相反最终结果 | 前两者不能覆盖最终状态；相反结果记冲突 |
| T21 | payment 记录已提交，但模拟调用前中断，再次 start_payment | 保持唯一支付和 UNKNOWN，不补发支付；等待显式模拟最终结果 |

落地测试还应对 R1 的金额上下界和数量上界做参数化检查。固定时钟、临时数据库和本地模拟适配器应由测试创建与清理，不读取生产配置，不要求真实凭证。

设计分支的最终报告应写明“已完成设计文档及静态核对；未修改业务代码、未运行支付测试、未部署”，并且只有确实执行过相应文档检查后才能这样报告。教学文档本身不证明上述动作已经发生。
