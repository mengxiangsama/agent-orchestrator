# 编排场景教学示例

> 本页全部内容都是教学示例，不是已经创建智能体、执行命令或通过验收的证据。任务 ID 是示例内的逻辑编号；“执行者 A/B”是角色称呼，不是真实工具返回的 agent ID。实际使用时必须先核对宿主能力，再记录真实 ID、文件差异和验证结果。

本页按 [Skill 核心规则](../SKILL.md)、[运行能力与降级](../references/runtime.md)、[分发与返回规范](../references/dispatch.md)、[任务记录规范](../references/ledger.md)和[验收规范](../references/acceptance.md)组织。文中的业务文件路径是合成项目的相对路径，不表示本 Skill 仓库包含那些文件；可点击的本地链接只指向本仓库真实文档。

## 1. 简单任务不拆分

**教学示例：修正一句说明。**

合成用户请求：

> 把 `docs/export.md` 中“导出包含所有搜索结果”改成“导出只包含当前页结果”。只改这一句，其他内容保持原样。

这是一个文件中的明确替换，不需要额外执行者。主智能体先查看目标句和已有改动，再完成修改；如果实际文件没有这句话，就报告具体差异，不猜测替换位置。

可以在回复中记录 `S1：主智能体；无依赖；仅写 docs/export.md；交付一句说明的修改`，不必为此创建任务表文件。

主智能体应检查该文件的实际差异，并确认新句与请求逐字一致、没有无关改动。`git diff -- docs/export.md` 可帮助检查已跟踪文件；若文件未被跟踪，还需直接打开文件，不能以空 diff 证明没有变化。这是文档检查，不需要将单元测试、构建或部署列为完成条件。

教学交付表述：“已修改目标句并检查文档差异；未执行业务测试，因为本次没有业务代码变更。”只有实际完成这些动作后，才可在真实回复中使用这句话。本页没有执行该示例。

## 2. 两个独立任务并行

**教学示例：整理两个互不依赖的接口说明。**

合成用户请求：

> 根据现有路由与校验代码，分别补齐用户查询和导出接口的说明。只编辑 `docs/user-api.md`、`docs/export-api.md`，不要改业务代码；可以委派两个独立执行者。

主智能体先检查真实工具的创建、通信、等待和停止语义，再确定本轮最多同时安排两个执行者。这个数字是本轮预算；平台并发上限如果没有公开，就记录为“未知”。没有相应工具时，使用第 6 节的降级流程。

| 任务 | 负责人 | 前置 | 可写范围 | 交付与验收条件 |
| --- | --- | --- | --- | --- |
| P1 | 执行者 A | 无 | `docs/user-api.md` | 用户查询的参数、默认值、错误响应与代码一致；每项附代码位置 |
| P2 | 执行者 B | 无 | `docs/export-api.md` | 导出的分页范围、参数、错误响应与代码一致；每项附代码位置 |
| M1 | 主智能体 | P1、P2 验收后才能整合 | 无文件写入 | 独立核对公共响应字段和两份文档的表述一致性 |

主智能体自己先读取公共响应类型、列出核验清单；执行者并行工作期间继续这项独立检查。P1/P2 只读同一份业务代码没有写入冲突。禁止把其中一方的可写范围扩大成 `docs/`，否则会与另一方形成父子目录写入冲突。

两个分发消息都必须包含必要背景、具体只读代码路径、精确可写文件、交付标准、单次执行预算和返回格式，而不是只说“按之前聊天补文档”。如果代码中缺少需要说明的默认值，执行者报告缺口，不替业务编造默认行为。

教学状态顺序：P1/P2 可同时从 `pending` 进入 `running`；任意一方返回后只记为 `submitted`。主智能体逐项核对真实内容和差异后，分别决定 `accepted` 或 `rework`。两个结果均验收通过后，M1 才检查整合后的字段、链接、重复说明和遗漏。

共享目录内应保留其他人的改动。即使使用隔离工作区，也仍需检查最终整合差异。提交状态保留文件所有权，不能因为执行者发来摘要就立即让其他执行者写同一文件。完成后按宿主的真实资源语义释放执行者，不把逻辑状态变化等同于资源已经释放。

## 3. 提交不等于验收

**教学示例：设计已返回，实现尚未获准启动。**

合成用户请求：

> 设计并实现一个导出模块。规则是只导出当前页，page 从 1 开始，page_size 为 1 到 100 的整数，按记录 ID 升序分页；非法分页参数返回 INVALID_ARGUMENT。先完成设计，再按通过验收的设计实现。

| 时点 | D1：设计 | I1：实现 | 主智能体动作 |
| --- | --- | --- | --- |
| 起点 | `running` | `pending` | 同时整理独立的整合检查清单 |
| 执行者返回设计 | `submitted` | `pending` | 打开 `docs/export-design.md` 检查范围与规则 |
| 发现遗漏 | `rework` | `pending` | 指明设计缺少“当前页”的页码和页大小约定 |
| 主智能体发起第 2 次执行 | `rework → running` | `pending` | 把遗漏规则和明确的通过标准发给 D1 |
| 修订后重新提交 | `submitted` | `pending` | 检查新内容，仍不派 I1 |
| 条件全部满足 | `accepted`，验收版本 1 | 可以进入 `running` | 派发 I1，并传递 D1 v1 的具体内容或可读快照 |

表格表示教学中的决策顺序，不是一次真实运行。最后一行的先决条件必须由主智能体实查后成立。

不能用“文件已经存在”“执行者说完成了”或“创建任务的工具调用成功”替代 D1 的验收。I1 提示词需要写明 `前置：D1，主智能体验收版本 1，docs/export-design.md`，并带上分页字段及规则摘要。若执行者看不到这个路径，应提供允许传递的快照或补丁；相同路径名不能证明内容版本相同。

## 4. 成果不合格后返工

**教学示例：实现违反明确的分页规则。**

沿用第 3 节的合成请求。假设主智能体在审查 I1 第一次提交时，实际发现 `src/export/service.py` 的 `export_page` 忽略了 `page_size`，会返回全部记录。这个条件构成本例的教学前提，不是对当前仓库的缺陷判断。

主智能体应定位真实代码位置，保存能复现问题的命令和输出，再将 I1 从 `submitted` 退回 `rework`。不得验收这份成果，也不得交给依赖它的集成任务。

以下是完整的教学返工通知；它只适用于上述合成项目：

```text
任务 ID / 下一次尝试：I1 / 2
决定：返工。由主智能体发起本次执行，执行者不得继续委派。
背景：用户明确要求只导出当前页。前置 D1 验收版本 1 不变。
原因：首次提交的 src/export/service.py 中，export_page 未使用 page_size，
      与已验收设计的当前页范围不符。实际使用此通知前，主智能体必须
      附上实查代码位置与复现输出；本教学文档没有这些运行证据。
当前有效输入：docs/export-design.md，D1 v1；page 从 1 开始，
              page_size 必须为 1 到 100 的整数；按记录 ID 升序分页。
允许读取：docs/export-design.md、src/export/、tests/export/。
允许修改：src/export/service.py、tests/export/test_page_export.py。
禁止事项：修改设计、其他文件、提交 Git、发布、部署或创建执行者。
通过标准：准备 ID 为 1 到 5 的记录，page=2、page_size=2 时只返回 3、4；
          page=4 时返回空集合；page_size=0 时返回设计规定的参数错误。
复测命令：在合成项目根目录运行
          python3 -m unittest discover -s tests/export -p 'test_*.py'
          同时检查上述两个文件的实际差异与调用方兼容性。
预算：默认共两次执行；本次为第 2 次，只执行本轮授权。
阻塞：设计不可读、约定冲突或验证环境缺失时向主智能体报告，禁止补猜。
返回：任务 ID、尝试、前置版本、submitted/failed/blocked、实际文件、
      命令/目录/退出码/关键输出、未验证项、未解决问题、范围偏差。
```

这份通知展示应提供的信息。本页未执行其中的命令；真实返工通知必须补齐已有的实查证据后才发送，不能把教学前提冒充日志。

I1 修订后仍返回 `submitted`。主智能体核对原缺陷、补充边界和最终差异，再决定是否验收。第二次执行后仍不合格时，保持未通过，记录剩余问题；只有出现新证据且仍在授权范围内，主智能体才能说明原因并调整预算，不能让执行者自行无限重试。

## 5. 子任务执行失败

**教学示例：环境缺少必要依赖，未生成可验收成果。**

合成用户请求：

> 只读检查 `src/reporting/` 的现有测试，报告测试结果和问题位置；不要修改代码、安装依赖或访问网络。

任务 F1 只读，执行者禁止改文件。以下是故障返回的教学样例，其中错误文字是合成演示，不是实测输出：

```text
任务 ID / 尝试 / 前置版本：F1 / 1 / 无
执行结果：failed
交付物：本回复中的诊断信息；无生成文件。
实际改动：无。
待核验命令：python3 -m unittest discover -s tests/reporting -p 'test_*.py'
工作目录：合成项目根目录，以 . 表示。
教学故障条件：测试收集阶段无法导入 reporting。
示意错误文本：ModuleNotFoundError: No module named 'reporting'
真实退出码和日志：本教学文档未执行命令，未取得。
未验证：测试用例没有运行，不能判断业务断言是否满足。
未解决问题：需要主智能体核对解释器、包布局与启动方式。
范围偏差：无；没有安装依赖或修改源文件。
```

在真实流程中，主智能体须拿到实际命令结果，并确认该次执行已经停止，才按 [记录语义](../references/ledger.md)记入 `fail`、释放任务占用。先只读核对工作目录、项目声明的运行环境和包布局；如果已有正确环境，可以在剩余预算内发起一次有明确原因的新尝试。如果需要用户未授权的联网安装，则报告 `blocked` 及缺失条件，不擅自扩权。

执行失败和成果不合格不同：前者可能没有可评审的交付物，后者已有内容但不满足要求。两者都不能触发下游任务。等待超时也不是失败证据；如果执行者仍在工作，保留状态并等待或按已授权的时限中断，确认停止前不重复派发同一写入范围。

## 6. 没有多智能体工具时降级

**教学示例：宿主只有文件和命令能力。**

合成用户请求：

> 设计并实现一个本地文本导出器，能拆分的话请并行推进。输出为 UTF-8，每行一条记录，按输入顺序写入；空输入生成空文件。不要联网或发布。

如果当前环境没有真正的子智能体创建能力，主智能体应直接说明：“当前可用工具不支持子智能体委派，我会按设计、核验、实现和整合的顺序完成。”不得打开新聊天冒充执行者，不得填写虚构 agent ID，也不得承诺后台继续工作。

教学安排如下：

| 阶段 | 负责人 | 开始条件 | 完成条件 |
| --- | --- | --- | --- |
| D1 设计 | 主智能体 | 用户规则清楚 | 明确输入类型、编码、空输入、写入错误及验证用例，完成设计核验 |
| I1 实现 | 主智能体 | D1 已核验并记录版本 | 按该版本实现，并取得风险相称的验证证据 |
| M1 整合 | 主智能体 | I1 已验收 | 检查真实调用路径、输出文件和异常行为 |

同一个主智能体承担所有阶段，依赖和验收门槛仍然存在；不要声称有独立执行者复核。若“现有输出文件是否允许覆盖”尚未确定，先完成不依赖该规则的设计部分，再向用户指出这个具体缺口，不能默认覆盖数据。

降级不会增加授权范围。本例没有发布步骤；实际最终报告需写明单智能体执行、完成了哪些阶段、真实检查结果和未验证项。本页不包含导出器实现或运行证据。

## 7. 只设计，不修改业务代码

**教学示例：支付模块的设计审查。**

合成用户请求：

> 阅读现有订单和优惠券接口，设计接入支付的方案，标出规则缺口和测试建议。只输出 `docs/payment-proposal.md`，先不要修改业务代码、测试或配置，也不要调用支付接口。

任务模式为 `design`。可以安排一个只写上述文档的设计任务；仅为凑齐角色而创建开发、测试任务没有意义。主智能体自己核对既有接口和文档，不把“验收可实施性”理解成实施授权。

设计应列出已知接口、数据流、状态迁移、失败路径、依赖和测试建议。若用户没有说明优惠券是否抵扣运费，应明确记录：“优惠券能否抵扣运费未定；该项会改变应付金额，必须由用户决定。”可以说明不同选择的影响，但不能把任何选项写成既定业务规则。

对于包含此类关键未决规则的文档，主智能体可以认定它满足“分析并列出缺口”的交付请求；但应将可供编码的 D1 验收保持 `blocked`，不能给出供 I1 使用的 `accepted` 设计版本。交付说明与编码前置验收是两件不同的事。

教学交付范围检查：只有 `docs/payment-proposal.md` 被修改，业务代码、测试、配置没有本任务写入；已有他人改动须单独辨认并保留。验证只包括文档内容、代码引用和范围核对，不应声称支付测试、线上流程或部署通过。

若用户提供了所有必要规则，主智能体可以完成设计验收后结束本轮，也仍然不能启动实现。一个规则完整、带前置版本交接的支付教学例子见 [优惠券订单支付模块](coupon-order-payment.md)。
