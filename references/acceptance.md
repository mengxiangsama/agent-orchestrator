# 主智能体验收与最终报告

## 验收前

核对 task ID、尝试、前置验收版本和写入范围；取得交付物的真实路径/差异。工具报告完成、进程退出 0、主智能体验收通过是不同的事实。

哪个任务先提交就先验收哪个，不等待其他无关任务完成。内部问题定向返工，不打断不受影响的并行任务；契约变化则协调受影响任务和版本，不能各自改约定。

按实际变更风险决定是否需要独立审查，不因文件位于支付/权限目录就机械增设角色。高风险或用户要求时使用 [独立审查流程](review.md)，由非实现者检查稳定候选成果。审查未完成或仍有阻塞项时，不提前标记 `accepted`；候选快照可供审查，但不等于可供下游实现使用的已验收前置。

## 验收记录模板

| 项目 | 主智能体应核对的证据 |
| --- | --- |
| 用户范围 | 分析/设计/审查未变成实施；实际变更未超出授权 |
| 内容存在 | 打开真实文件，检查 diff/文件列表，不只读摘要 |
| 单项质量 | 每条验收条件对应实际输出或测试结果 |
| 接口与业务 | 字段名、类型、单位、空值、错误、业务规则与已验收前置一致 |
| 跨任务关系 | 独立成果间无冲突/遗漏，没有使用已失效设计 |
| 验证证据 | 命令、目录、退出码和输出可核验；区分运行测试、静态检查、未执行 |
| 独立审查（适用时） | 是否需要及原因；非实现者身份、候选标识、问题与复查结论；未满足的关卡明确列出 |
| 决定 | accepted + 版本，或 rework/blocked + 原因与标准 |

对代码至少执行风险相称的测试/构建/静态检查；最后做必要的集成验证。环境无法执行时如实记录，不将“看起来正确”升级为运行通过。

返工后先验证原问题是否解决，再检查修复引入的差异及受影响回归。独立审查指出的问题由原审查者或另一名非实现者定向复查，主智能体核对证据后决定；换人须交接原问题和候选版本。复查不机械重跑所有检查，也不能跳过修复所影响的用例；超出原范围或改变契约时重新评估风险和受影响任务。各任务与必要复查通过后，最终仍做整体集成检查。

模块的 `accepted` 只表示其已达到本任务验收标准。记录测试用了真实依赖还是替身；消费方与提供方按共同契约完成单项验收后，才进行真实成果集成。集成时核对实际调用、字段类型和业务行为，不能凭两份通过报告就声称整体可用。详见 [协作边界与并行](parallel-boundaries.md)。

对设计检查需求覆盖、关键规则来源、依赖、接口、异常路径、未决问题和验收可实施性。业务规则未决的设计不得作为编码的已验收输入。

对审查交付可定位的问题、影响、证据及不确定性；不因发现问题就擅自修改。

## 最终报告模板

```text
结论：完成 / 部分完成 / 阻塞；与原始请求对应的成果。
交付物：实际路径/链接及用途。
调度摘要：是否使用子智能体、实际创建数量/任务、依赖和关键验收决定。
验证：实际运行的命令与结果；静态/文档检查另列；集成检查结果。
审查（适用时）：风险判断、审查者与候选标识、问题关闭情况、定向复查结论；缺少独立审查时明确披露。
未验证：缺少的环境、权限、外部服务或未覆盖的平台。
限制/风险：仍然存在的问题，不夸大 Skill 的能力。
必要后续：需要用户决定的具体事项；没有则不制造确认步骤。
```

发布或部署只有用户授权且实际完成时才能报告。将“本地生成”“测试通过”“提交”“推送”“线上验证”分别表述。
